Project Three

Introduce the Problem

Housing prices affect everything from personal finances to city planning, and estimating a home’s value is a core task for buyers, sellers, lenders, and appraisers. With today’s rich property data, we can ask a practical question: Can we predict a home’s sale price from its physical characteristics and location-related features?

This project explores that question using the Kaggle House Prices: Advanced Regression Techniques dataset. It includes detailed residential properties from Ames, Iowa, with features such as lot size, neighborhood, overall material/finish quality, year built and remodeled, basement and above-ground living areas, number of bathrooms and bedrooms, garage capacity, and more. By analyzing patterns across these features and training predictive models, the goal is to understand which factors matter most—and how accurately we can estimate a home’s SalePrice.

For evaluation, we will follow the competition’s approach and use Root Mean Squared Error (RMSE) (on log-transformed prices when appropriate). The data are provided in two files:

  • train.csv — includes both features and the target SalePrice.
  • test.csv — includes the same features without the target; predictions on this file can be submitted to Kaggle for a public score.

The purpose is not only to measure model performance but also to reflect on broader implications. If machine learning can estimate sale prices well, it could help streamline valuations and provide transparency for buyers and sellers. However, it also raises questions about fairness and bias (e.g., neighborhood effects), explainability (why a model priced a home a certain way), and data drift (how changing markets can degrade a model over time). We will keep these considerations in mind as we build and evaluate our models.

What is regression and how does it work

Regression is a supervised learning approach for predicting a continuous value. In this project, that value is a home’s SalePrice. We train on many past sales where features (lot size, quality, square footage, year built, neighborhood, etc.) and the final price are known. The model learns patterns that map features → price, then we test how well it predicts prices for new homes.

Linear Regression (required baseline)

Linear regression estimates price as a weighted combination of the input features plus an intercept (baseline). Each weight shows how much that feature tends to move the price when other features are held fixed. We’ll use scikit-learn’s LinearRegression as our starting point.

Why preprocessing matters here
  • Handle missing values (e.g., median for numeric, most frequent for categorical).
  • Encode categoricals (e.g., one-hot encoding) so the model can use them.
  • Tame skew/outliers (often log-transforming areas and using log(SalePrice) for stability).
  • Optionally standardize numeric inputs (especially helpful for some regularized linear models).
How we’ll measure success

We’ll evaluate with Root Mean Squared Error (RMSE), aligned with the competition’s metric (often computed on log prices). Lower RMSE means more accurate price estimates. We’ll keep this metric consistent across experiments so improvements are easy to compare.

Limitations to keep in mind
  • Relationships might not be perfectly linear; we may need transformations or different models.
  • Some features can be redundant (multicollinearity), which can blur individual effects.
  • Housing markets shift over time, so models can drift without updates.

Experiment 1: Data Understanding

Goal. Before modeling, I want a high-level picture of the data: what the target looks like, which features might matter, where missing values live, and whether there are outliers or obvious data-quality quirks that could mislead a regression model.

Dataset shape & target
  • train.csv: 1,460 homes, 81 columns (including SalePrice).
  • test.csv: 1,459 homes, 80 columns (same features, no SalePrice).

Target (SalePrice) is continuous and typically right-skewed (a few very expensive homes). I plan to consider log(SalePrice) during evaluation/modeling to reduce skew and stabilize variance.

First pass checks I will run
  • Missingness map: Identify features with substantial missing values (e.g., some basement/garage/porch attributes can be missing when the feature doesn’t exist). Distinguish between true missing vs. not applicable.
  • Dtypes overview: Split into numeric vs categorical features. Numeric includes areas, counts, years; categorical includes neighborhood, exterior materials, quality/condition categories, etc.
  • Basic sanity checks:
    • Non-negative areas (e.g., LotArea, GrLivArea, TotalBsmtSF).
    • Reasonable year ranges (YearBuilt, YearRemodAdd, YrSold).
    • Counts within sensible bounds (e.g., bathrooms, bedrooms, garage cars).
Target & key feature relationships (what I expect to see)
  • Overall quality (OverallQual): Typically one of the strongest single predictors; higher quality ↔ higher prices.
  • Size measures: GrLivArea and TotalBsmtSF often correlate strongly with price; total space tends to matter.
  • Garage capacity/area: GarageCars and GarageArea add signal (capacity tends to be cleaner than raw area).
  • Age & updates: YearBuilt, YearRemodAdd (and “age at sale”) can relate to price; newer or recently remodeled homes may command higher prices.
  • Location proxy: Neighborhood often captures location-driven price differences.
I’ll quantify these with:
  • Correlation heatmap (numeric only) to spot top numeric predictors (e.g., OverallQual, GrLivArea, GarageCars, TotalBsmtSF, YearBuilt).
  • Box/violin plots of price by categoricals (e.g., Neighborhood, OverallQual, HouseStyle) to see separability across groups.
  • Scatter plots (price vs GrLivArea, TotalBsmtSF, etc.) to see trend shape and potential heteroscedasticity.
Outliers & influential points

Known pattern in this dataset: a few homes with very large GrLivArea but relatively low price can act as influential outliers for linear models. I’ll visualize price vs. GrLivArea (both raw and log-price) and consider robust handling later (e.g., transformations, robust models, or careful outlier policy).

Collinearity & redundancy

Space/size features can be correlated (e.g., GarageArea vs GarageCars, or multiple porch/basement sub-areas). I’ll watch for multicollinearity, as it can destabilize linear coefficients, and plan to:

  • Prefer cleaner proxies (e.g., GarageCars over GarageArea) when two features convey the same signal.
  • Consider combining related features into a single engineered metric (e.g., total square footage).
Train vs. test alignment (data leakage guardrails)
  • Compare feature distributions between train and test (especially categoricals like Neighborhood) to ensure encodings align and to avoid using any information from test during training (no peeking at the target, no target-based transforms).
  • All preprocessing steps will be fit on training data only and then applied to validation/test.
Visuals I plan to include (in the notebook/blog)

  • Relationship: log(SalePrice) vs GrLivArea (size).
  • Relationship: price by quality (OverallQual boxplot).
  • Quick signal check: top 10 numeric correlations with SalePrice (bar chart).
Outcome of this step

A prioritized list of promising features, a short list of risky/outlier patterns, and a concrete preprocessing plan for Experiment 1 (impute missing values, one-hot encode categoricals, and consider log-transforming the target). This sets up the baseline model fairly and transparently.

Experiment 1 — Pre-processing

Goal. Prepare a clean, model-ready table with minimal but sensible steps so the baseline is fair and reproducible.

What needs to happen after data understanding
  • Separate target & drop identifiers
    • Target: SalePrice (will use log transform for modeling).
    • Drop Id from features (identifier only).
  • Handle missing values (nulls vs. “not applicable”)
    • Numeric features: median imputation (robust to skew/outliers).
    • Categorical features: most-frequent imputation.
    • Note: Some fields are “missing because the feature doesn’t exist” (e.g., no basement/garage). For baseline simplicity, still impute them; one-hot encoding will capture “no feature” as its own level where appropriate.
  • Transform features to numeric
    • Apply one-hot encoding to all categorical columns.
    • Use handle_unknown='ignore' so unseen categories in validation/test don’t break the pipeline.
Target transformation
  • Model on log(1 + SalePrice) to reduce right-skew and align with the competition’s log-RMSE style evaluation.
  • At prediction time, convert back with expm1 for dollar-RMSE reporting or Kaggle submission.
Feature set for the first experiment (keep it broad)
  • Use all available features except Id and the target.
  • Rationale: for a baseline, broad coverage + one-hot lets the model find signal without premature pruning. We’ll consider pruning/engineering later.
What I’m not doing yet (by design)
  • No scaling (OLS doesn’t require it; we’ll revisit for regularized models).
  • No outlier removal (keeps baseline honest; we’ll reassess after we see residuals).
  • No engineered features yet (e.g., TotalSF, AgeAtSale), saving these for Experiment 3.
Why these choices
  • Median/mode imputation + one-hot is a simple, reliable starting point for mixed-type tabular data.
  • Log-transforming the target typically stabilizes variance and makes errors more comparable across cheap vs. expensive homes.
  • Using all features prevents discarding valuable signal too early; later experiments will test regularization, feature engineering, or selection.

Experiment 1 — Modeling (Linear Regression)

Goal. Build a simple, fair baseline model.

Model. I used Linear Regression (ordinary least squares) from scikit-learn. The model is wrapped in a pipeline that applies the Experiment 1 preprocessing (median imputation for numeric features, most-frequent imputation + one-hot encoding for categoricals), then fits a linear model on the log-transformed target log(1 + SalePrice). I trained with an 80/20 train–validation split and a fixed random seed for reproducibility. I did not tune hyperparameters in this baseline; the goal was to establish a transparent starting point before adding regularization or feature engineering in later experiments.

Why linear first? Linear regression is fast, interpretable, and gives a strong baseline on tabular data. Using the log target stabilizes variance and aligns with the competition’s log-RMSE evaluation style.

Experiment 1 — Evaluation

Metric
  • log-RMSE (validation) — error measured in log-price space (matches Kaggle’s scoring style).
  • RMSE in dollars (validation) — predictions inverted back to dollars for an intuitive sense of average error.
Results
  • Validation log-RMSE: 0.13846
  • Validation RMSE (USD): $[25,418]
  • Kaggle public score (log-RMSE): 0.13846
Interpretation

A log-RMSE of ~0.138 implies roughly 14–15% typical relative error, which is a strong baseline for this dataset. The model already captures core signals (overall quality, living area, etc.) with minimal preprocessing.

Limitations & next steps

Coefficients in a plain linear model can be sensitive to multicollinearity and skewed features, and high-cardinality categoricals can increase sparsity. In the next experiments I’ll add regularization (Ridge/Lasso), consider standardizing numeric features, handle skewed variables more deliberately, and introduce feature engineering (e.g., total square footage, age at sale) to see if I can improve on this baseline.

Experiment 2 — Regularized Linear (Ridge) + Skew Fix + Standardization

Goal. Improve generalization over the baseline OLS by reducing overfitting and taming skew.

What changed vs. Experiment 1
  • Regularization: Switch from plain OLS to Ridge (L2). This shrinks coefficients on noisy/high-dimensional one-hot features and combats multicollinearity.
  • Skew fixes (numeric subset): Apply log1p to highly right-skewed numeric features (areas) so their effect is more linear and less dominated by extreme values.
  • Standardization: After one-hot expansion, apply a StandardScaler(with_mean=false) to the whole sparse design matrix so Ridge treats features on comparable scales.
  • Same target: Train on log(1 + SalePrice) and report log-RMSE (plus $ RMSE).
Why this helps

Ridge reduces variance from many correlated/expanded features; log-transforming skewed inputs makes linear relationships more linear; standardization matters because ridge penalties are scale‑dependent.

Expected outcome
  • Validation log-RMSE should typically beat the baseline (~0.13846) by a noticeable margin.
  • Coefficients are more stable; less overfit to rare categories.

Experiment 2 — Results & How They Compare to Experiment 1

Score
  • Validation/Kaggle-style log-RMSE: 0.13342
  • Baseline (Exp 1) log-RMSE: 0.13846
Change vs. Exp 1
  • Absolute improvement: 0.00504 lower log-RMSE.
  • Relative improvement: ~3.64% better than the baseline.
  • In plain terms: typical relative error moved from ≈14.85% to ≈14.27% (using e^(log-RMSE) - 1), ~4% reduction in relative error.
Why it likely improved
  • Ridge regularization shrank noisy coefficients from the large one-hot design, reducing overfitting and stabilizing weights with multicollinearity.
  • Log1p transforms on skewed numeric features (e.g., GrLivArea, TotalBsmtSF, 1stFlrSF, LotArea, MasVnrArea) made relationships more linear and less driven by extremes.
  • Standardization put features on comparable scales so Ridge’s L2 penalty is applied fairly across numeric and one-hot columns.
What still looks improvable
  • Linear models can miss mild nonlinear interactions (e.g., size × quality, age × remodel).
  • High-cardinality categoricals (e.g., Neighborhood) may still introduce sparsity and subtle over/under-penalization.
  • Feature semantics aren’t fully captured yet (e.g., combining areas into a TotalSF, or constructing AgeAtSale, BathsTotal, PorchSF).
Takeaway

Experiment 2 delivers a meaningful, consistent bump over the baseline with modest complexity. The model is more robust and generalizes better—exactly what we wanted from regularization and skew handling.

Experiment 3 — Feature Engineering + Random Forest (Non-linear)

What I changed (vs. Experiments 1–2)

I added light feature engineering to capture domain meaning and switched from linear models to a tree-based model to learn non-linearities and interactions.

Engineered features
  • TotalSF = GrLivArea + TotalBsmtSF, AgeAtSale = YrSold − YearBuilt, RemodAge = YrSold − YearRemodAdd
  • BathsTotal = FullBath + 0.5·HalfBath, PorchSF = OpenPorchSF + EnclosedPorch + 3SsnPorch + ScreenPorch
  • Flags: HasBsmt, HasGarage, HasFireplace, HasPool
Model & preprocessing
  • Model: RandomForestRegressor (600 trees).
  • Preprocessing: same as before (median/mode imputation + one-hot for categoricals). Trees don’t need scaling.
  • Target: still log(1 + SalePrice) to align with log-RMSE.
Results
  • Experiment 3 log-RMSE: 0.14311
  • Experiment 2 (Ridge) log-RMSE: 0.13342
  • Experiment 1 (Linear) log-RMSE: 0.13846
How it changed from the previous experiment
  • Compared to Exp 2, performance worsened by +0.00969 log-RMSE (≈ 7.3% relative).
  • Compared to Exp 1, it’s +0.00465 worse (≈ 3.4% relative).
Why this likely happened (diagnosis)
  • High-cardinality one-hot features (e.g., Neighborhood) can be noisy for forests; trees may split on rare categories that don’t generalize.
  • The “default” forest can underfit/overfit without tuning (max_depth, min_samples_leaf, max_features), especially with sparse, wide matrices from one-hot.
  • Linear signals dominate this dataset (size/quality). Ridge leverages them well; a plain forest without careful tuning/GBM may not beat a well-regularized linear model.
  • Some engineered features may be redundant with existing columns, adding noise more than signal.
What I learned

Non-linear models don’t automatically win on tabular data with many one-hot categoricals. Here, a regularized linear model (Exp 2) captured the major effects more cleanly than an untuned forest with sparse inputs.

Storytelling & Impact

Impact

Building a house-price predictor isn’t just a technical exercise—it sits inside real markets, policies, and people’s lives. Here are the key potential benefits, risks, and mitigations I considered.

Potential benefits
  • Consistency & speed: Automated estimates reduce turnaround time and noisy human variation in valuations (helpful for buyers, sellers, agents).
  • Transparency for comparisons: Feature-level effects (e.g., size, quality) can make pricing more explainable than gut feel, especially with simple linear models.
  • Scenario planning: Stakeholders can explore what‑ifs (e.g., “What if we finish the basement?”) to make more informed renovation or listing decisions.
Risks & negative externalities
  • Proxy bias / disparate impact: Categorical features like Neighborhood can encode historical inequities (e.g., redlining). Even without protected attributes, proxies can reproduce disparities in lending, appraisals, or taxes.
  • Feedback loops: If many actors price off the same model, its estimates can become self‑fulfilling, amplifying existing price gaps or gentrification patterns.
  • Overreliance: Treating a point estimate as truth ignores uncertainty and data drift (e.g., sudden market shocks), leading to mispricing or unfair decisions.
  • Privacy & consent: Training on detailed property data can raise questions about what was collected, who consented, and who can access the model’s outputs.
  • Unequal errors: Errors may be larger for homes with rare attributes or in underrepresented neighborhoods, shifting costs onto specific groups.
  • Interpretability gap: More complex models (trees/boosting) can outperform linear models but make it harder for consumers to understand why a price was assigned.
How I would mitigate
  • Fairness review of features: Limit or carefully handle obvious proxies (e.g., Neighborhood) and test with/without them; document trade‑offs.
  • Slice metrics: Report RMSE by subgroup (price bands, neighborhoods, home types) to detect uneven performance; if gaps exist, address them (rebalance data, add features, or adjust loss).
  • Uncertainty & guardrails: Publish prediction intervals (not just point estimates). Require human‑in‑the‑loop for high‑stakes uses (loans, taxes, insurance).
  • Model cards & versioning: Document data sources, time range, assumptions, known failure modes, and update cadence; monitor data drift over time.
  • Regularization & simplicity: Favor simpler models when accuracy is comparable to preserve explainability and reduce overfitting on spurious signals.
  • Ethical use policy: Restrict use to informational support, not as the sole determinant for lending/insuring/pricing; audit downstream decisions for disparate impact.
Bottom line

This project can improve consistency and transparency in home valuations, but it also carries fairness, privacy, and overreliance risks—especially around location proxies and shifting markets. The responsible path combines careful feature choices, slice‑level evaluation, uncertainty reporting, and human oversight so the model informs decisions without quietly hard‑coding historical inequities.

Conclusion

This project gave me hands-on practice turning a raw tabular dataset into a working regression pipeline and showed how specific choices change performance.

What worked best
  • Target log transform (log(1 + SalePrice)) was the single biggest stability win. It made errors more comparable across cheap vs. expensive homes and helped every model behave better.
  • Simple, consistent preprocessing (median imputation for numeric, most‑frequent + one‑hot for categoricals) was enough to get a strong baseline.
  • Regularization matters. Moving from plain OLS to Ridge (with light skew fixes and standardization) improved log‑RMSE from 0.13846 → 0.13342. Shrinking coefficients helped with multicollinearity and the many one‑hot columns.
What didn’t help (as used here)

My first non‑linear attempt—Random Forest with light feature engineering—did not beat Ridge (0.14311). Even with features like TotalSF, AgeAtSale, BathsTotal, etc., an untuned forest on a very wide, sparse one‑hot matrix underperformed. Lesson: on this dataset, well‑regularized linear models set a high bar unless tree/boosting models are carefully tuned.

Feature selection & inclusion/exclusion
  • I intentionally started broad (use all features except Id) so the baseline wouldn’t miss important signal. With Ridge, this wide set performed better than early pruning.
  • Preliminary coefficient/importance checks suggest some redundancy (e.g., overlapping area features). A structured feature selection pass (e.g., removing highly collinear features, or combining them into TotalSF) is a good next step, but the regularized model already handled redundancy reasonably well.
  • Location proxies (e.g., Neighborhood) are powerful but raise fairness concerns; I would report slice metrics with and without them and document trade‑offs.
Key takeaways
  • Good preprocessing beats fancy modeling when data are tabular and mostly linear in spirit.
  • Regularization + light transforms (and standardization for penalized models) delivered the biggest improvement.
  • Non‑linear models need tuning (depth, leaf sizes, features) or gradient boosting to surpass a strong Ridge baseline.
  • Clear evaluation discipline (same split, same metric) makes comparisons meaningful.
If I continued
  • Try HistGradientBoostingRegressor / XGBoost / LightGBM with careful tuning and early stopping.
  • Add a small set of interaction features (e.g., OverallQual × TotalSF) and test whether Ridge/ElasticNet benefits.
  • Do feature audits (drop/keep experiments, grouped encodings for high‑cardinality categoricals) and report slice‑level RMSE to check fairness and robustness.
  • Produce prediction intervals to communicate uncertainty.

Overall, I learned that a disciplined baseline plus targeted regularization can be hard to beat, and that the best gains come from thoughtful preprocessing, not just swapping models.
